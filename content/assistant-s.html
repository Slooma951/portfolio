A personal desktop assistant for study, AI conversations and practical computer tasks. Built with Electron, a JavaScript interface and a local Node.js service.

Why I am building S

I wanted an assistant I could study with, talk to and use to carry out useful tasks on my computer. The aim is to get as much useful AI capability as possible while keeping usage down, rather than sending every small action to a model.

My longer-term goal is my own capable S model, developed toward a broad set of professional features that can run locally and offline with modest resource use. That is an ambition, not a completed result. The current implementation retrieves saved lessons as context. It does not train model weights, and fully featured offline operation and low-power performance have not been demonstrated.

What is in the current implementation

The source includes typed and spoken conversations, study modules and planning, local memory, provider routing, browser tasks, career documents, habits, calendar, code and activity workspaces. The current home screen is a voice-reactive Three.js shape. Account connections, installed models and device permissions determine which features are available on each computer.

How the architecture works

  1. The Electron interface sends a request to an authenticated local HTTP and WebSocket service.
  2. A rule-based router classifies the task and checks provider readiness and saved usage-limit cooldowns.
  3. The engine adds relevant local memory and bounded conversation context. Simple local actions and cached answers can avoid another model call.
  4. Provider adapters connect to Codex, Claude, Grok and Gemini. An optional Ollama route handles ordinary text questions; it is excluded from tasks requiring files, web or connector tools.
  5. Results return to the interface. Browser actions that may commit changes have review controls.

The local service binds to loopback and applies token, Host and Origin checks. These are source-visible controls, not a claim that the whole product has passed a security audit. Cloud providers and connected services still require network access.

Technology and engineering decisions

JavaScript and Node.js handle orchestration and the local service. Electron, HTML and CSS provide the desktop shell and workspaces; Vite bundles the interface, and Three.js renders the scene. Python supports an optional Chatterbox speech service. SQLite and Markdown support memory, while Git and Node's test runner support development and regression checks.

Assistant S integrates existing AI models. It is not a foundation model built from scratch, and an available adapter does not mean its provider account is currently signed in. AI coding assistance has been used during development and review.

Challenges and what the work taught me

Windows launch contexts
Settings and sign-ins could resolve to different AppData locations. Home-folder storage and migration handling address that difference. Desktop behavior needs checking from the ways the app is actually launched.
Provider limits and failures
Readiness checks, persistent cooldowns and alternate routes preserve useful work when a provider is unavailable. A fallback should carry the original task forward and report failures honestly.
Voice, rendering and local inference
Microphone recovery, restrained rendering and reduced-motion behavior share a limited device budget. Claims about responsiveness or power use need measurements on the target hardware.
Useful memory
Filtering unsuitable lesson fragments and retaining provenance makes retrieved context more useful. Persistence alone does not make a model better or a remembered fact current.

Evidence and next steps

The public showcase contains a runnable JavaScript interface-state example with synthetic inputs. Its eight tests passed on 17 November 2026. Those checks cover that isolated example, not the current complete application, voice pipeline or external integrations.

Next work includes evaluating local-model capabilities, measuring offline coverage and resource use, improving connection diagnostics, strengthening integration checks and adding current screenshots from a safe demonstration state. These are development directions, not promised release dates.
